## Целевые правила финансового ядра

1. У операции есть immutable UUID, owner, currency, positive canonical amount, type, occurred_at, created_at, source и revision. Opening balance хранится явно. Изменение остатка вручную — отдельная корректировка с причиной, а не скрытая перезапись.
2. Для одного счёта: `balance = opening_balance + income - expense + transfer_in - transfer_out + adjustments`. Перевод внутри одной валюты сохраняет суммарный баланс. Удаление/сторнирование является обратной операцией; повтор удаления не повторяет возврат.
3. В первой безопасной версии поддерживать точную сумму и итоги отдельно для каждой имеющейся валюты; новые FX-переводы отклонять. Если выбрана RUB-only версия, существующие валютные данные сохранять и явно показывать ограничение; не конвертировать их автоматически.
4. Предложение: Decimal на backend из строк, fixed scale для поддерживаемой валюты; в JSON decimal string, в UI minor units для вычислений в допустимом безопасном диапазоне. Не держать независимые float-формулы в экранах. Альтернатива — minor units end-to-end; решение закрепить одним ADR.
5. Input с лишними дробными знаками по умолчанию отклонять. Для явно разрешённых расчётов/FX согласовать округление, например HALF_UP, и момент применения. Не выдавать эту политику за требование RFC.
6. Один use case владеет DB commit: проверка владельцев, проверка payload, изменение журнала и всех балансов, ключ повтора, audit event — атомарно. Отправка Telegram идёт после commit, её сбой не откатывает успешную запись и не провоцирует новую.
7. `UNIQUE(user_id, client_id)` плюс hash содержимого; одинаковый ключ/тело возвращает прежний результат, другой payload — 409. Для Telegram отдельный ключ `(bot_id, update_id, operation_index)`. Разница идентификаторов HTTP/Telegram документирована.
8. Отклонять устаревшее редактирование по revision (409 или If-Match/412, выбрать контракт). Транзакция и optimistic version нужны также для update/delete, не только create.
9. Необратимые операции над финансовой историей заменить архивированием/сторнированием там, где история нужна; нельзя бесследно удалить половину перевода.

## Срезы рефакторинга без полной переписи

Предлагаемая структура, ещё не создана:

```text
bot/app/
  domain/             money, currency, transaction rules, errors
  application/        create/edit/reverse transaction, onboarding
  repositories/       account/transaction/category queries, unit of work
  services/analytics/ period totals, reconciliation
  integrations/       telegram, ai_provider, speech, ocr
  api/                thin routes, auth, DTO/error mapping
  bot/                thin handlers, confirmation flow
frontend/src/
  api/                transport, generated types, domain endpoints
  domain/             formatting, amount validation (no balance ledger)
  state/              queries, mutations, draft state, user cache
  features/           accounts, categories, transactions, analytics, capture
  demo/               isolated synthetic fixtures
```

Сначала characterization tests фиксируют только корректные сценарии; явно сломанное поведение фиксируется новым ожидаемым результатом, а не увековечивается снапшотом. После Money и auth можно извлекать transaction use cases, затем transport/cache, затем большие модальные окна. Не объединять смену СУБД, React major и переписывание всех экранов в один PR.

## Что осовременить и чего пока не добавлять

- Сохранить Python/FastAPI/aiogram/SQLAlchemy и React/TypeScript/Vite: сборка прошла, дефекты находятся в логике и интеграции. Обновлять проверенными небольшими шагами, не по слову latest.
- Зафиксировать Python 3.12.x или другой согласованный supported runtime, Node LTS с точной версией; на Mac проверить архитектуру arm64/x86_64. Существующий прогон был Windows/Python3.11/Node25 — это не target-сертификация.
- Ввести один backend lock (uv.lock либо hash-pinned requirements), отдельные runtime/dev зависимости; сохранить frontend package-lock и npm ci. Проверять upgrades в CI. Не добавлять одновременно два менеджера среды.
- Alembic — один способ эволюции схемы. PostgreSQL для серверной многопользовательской среды; SQLite для локальных тестов/одного экземпляра с корректными constraints. Поддержка двух БД означает два integration jobs.
- TanStack Query возможен для серверных запросов/мутаций и повторного использования кэша. Zustand добавлять только при необходимости сложного UI state. Ни одна библиотека не исправляет авторизацию, бухгалтерию или offline conflict автоматически.
- Минимальный CI: ruff, type check, pytest, frontend typecheck/build, Vitest, выбранные integration flows, dependency audit. Дальше Playwright для основных путей. Крупные e2e не заменяют быстрые money tests.
- Redis, Kubernetes, event sourcing и полноценный двойной бухгалтерский ledger не обязательны для этого масштаба. Durable drafts/idempotency сначала можно хранить в основной БД.

## Карточка любой будущей задачи

ID и связанные findings → наблюдаемый сценарий → контракт правильного поведения → затрагиваемые файлы → тест до изменения → узкая правка → тест после → обновлённая документация → ограничения → commit/rollback. Один ответ AI «готово» без вывода проверки задачу не закрывает.
