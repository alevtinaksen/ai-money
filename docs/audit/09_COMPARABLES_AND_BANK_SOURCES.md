# Аналоги, опыт разработки и доступность банковских данных

Дата: 26.09.2026. Дополнение к исследованию04 и гипотезе08. Ни одна функция здесь не реализована в AI Money на стадии аудита.

## Резюме

Практики Actual Budget, Firefly III и GnuCash дают проверяемые ориентиры для сверки, импортных соответствий, дублей и переводов. Конкретная доступность retail выгрузки банка Алины пока не установлена. Поэтому первый этап — один фактический формат с обезличенным образцом, а не универсальный коннектор ко всем банкам.

## Ключевые находки

Полезный минимальный продукт: понятный preview, точные денежные поля, source links, консервативный dedup, ручное подтверждение и сверка. Полный offline/FX и direct banking API имеют отдельную сложность и не обязательны для первой безопасной версии. Документированные developer practices — небольшие изменения, разделённые виды тестов, миграции — переносимы без копирования чужого кода и tooling.

## Источники

Ссылки и точные разделы приведены рядом с каждым утверждением в двух материалах ниже. Origin groups: официальная документация Actual; официальная документация Firefly в GitHub; manual GnuCash; официальные страницы/индекс банка (только предварительные сведения); Банк России. Повторные публикации одного поставщика не считаются независимыми подтверждениями.

# Сопоставимые приложения: практики для AI Money

Дата чтения: 26.09.2026. Метод: поиск → открытие официальной документации/официального репозитория документации → отделение существующей функции от нашего предложения. Это исследование продуктовых решений, не сравнительный тест быстродействия, не рекомендация мигрировать реальные данные и не подтверждение доступности банковских интеграций. Приложения не устанавливались. Код не копировался.

## 1. Actual Budget: импорт, переводы, сверка

**Подтверждено документацией.** CSV-импорт позволяет сопоставить колонки, увидеть трактовку даты, менять знак суммы и использовать раздельные debit/credit. Для борьбы с дублями сначала используется идентификатор, затем сочетание даты, суммы и получателя; импорт может сопоставиться с ручной записью. Восстановление ранее удалённых строк при импорте является отдельной настройкой и по умолчанию включено; это существенно при повторном импорте. [Importing Transactions](https://actualbudget.org/docs/transactions/importing/), разделы Import CSV Files, Avoiding duplicate transactions (прочитанные строки 73–103).

**Наше предложение.** После A0–A6 сделать импорт сначала в staging-черновик: исходная строка → разобранные дата/валюта/сумма → выбранный счёт → найденный возможный дубль → подтверждение. Повторная загрузка файла не должна молча восстанавливать удалённую операцию. Не считать два одинаковых кофе в один день гарантированным дублем: нечёткое совпадение — кандидат для человека. Тест: один файл дважды, ручная запись+импорт, два одинаковых реальных платежа, запятая/точка и неоднозначная дата.

**Подтверждено документацией.** Перевод в Actual связывает две стороны; сумма синхронизируется, удаление убирает обе стороны. Даты могут различаться, поскольку банк списывает и зачисляет в разные дни; статусы сверки также отдельные. Две уже импортированные записи можно связать при разных счетах и одинаковых противоположных суммах. [Transfers](https://actualbudget.org/docs/transactions/transfers/), Modifying a Transfer / Deleting a Transfer / Make a Transfer from Two Existing Transactions (строки 72–113).

**Наше предложение.** Исправить FE-02/12 на уровне одной финансовой команды. В дальнейшем поддержать явную связь импортированных сторон, а не угадывать по слову «перевод». Не обязательно копировать модель из двух строк: AI Money может оставить один объект transfer с атомарными двумя изменениями остатков. Даты списания/зачисления добавлять только после появления соответствующего сценария.

**Подтверждено документацией.** Сверка Actual сравнивает выписку с журналом, различает проверенные и непроверенные операции, показывает разницу, затем позволяет закрепить сверенные строки; редактирование закреплённой строки требует предупреждения. [Reconciliation](https://actualbudget.org/docs/accounts/reconciliation/), Work Flow / Starting the Reconciliation Tool (строки 58–94).

**Наше предложение.** Добавить после A5 отдельный экран «Сверить со счётом»: дата выписки, остаток банка, расчётный остаток, разница, список неподтверждённых строк. Не исправлять несовпадение скрытой перезаписью balance. Если корректировка нужна, создать явную операцию с причиной. Проверка: внесён пропущенный расход — разница исчезла; «пересчитать» не скрывает дефект журнала.

## 2. Actual Budget: реальная offline-архитектура и её границы

**Подтверждено документацией.** Actual описывает локальное хранение, работу без сети и последующую синхронизацию с выбранным сервером. Сброс синхронизации назначает выбранную копию исходной и может отменить несинхронизированные правки других устройств. Документация предупреждает о конфликтах одновременного редактирования общего бюджета. Опциональное end-to-end шифрование не покрывает локальные данные и банковские токены. [Syncing Across Devices](https://actualbudget.org/docs/getting-started/sync/), введение / End-to-End Encryption / Resetting Sync / Multi-user Support (строки 30–47,63–75,101–103).

**Наше предложение.** Не называть сегодняшние localStorage overrides AI Money offline-first. На ближайшем этапе оставить online-write+локальные черновики из A4. Полный offline — отдельный проект с очередью команд, ревизиями, разрешением конфликтов, восстановлением и тестами двух устройств. Не предлагать кнопку «сбросить синхронизацию» без предварительного экспорта несинхронизированных записей и объяснения последствий.

## 3. Actual Budget: валюты — важное ограничение аналога

**Подтверждено документацией.** Страница прямо сообщает об отсутствии нативной мультивалютности и описывает обходной подход через экспериментальные шаблоны правил. Это не основание считать Actual полноценным эталоном валютного учёта. [Multi-Currency](https://actualbudget.org/docs/budgeting/multi-currency/), вводный раздел и warning (строки 43–51).

**Наше предложение.** Для FE-10 использовать собственный явный контракт валют, не копировать фиксированный множитель как универсальную конвертацию. Сначала показывать суммы отдельно по валютам и запрещать FX-переводы; расширение — только с исходной суммой, полученной суммой, курсом/датой и правилами округления.

## 4. Firefly III Data Importer: повтор и происхождение данных

**Подтверждено официальной документацией в GitHub.** Импорт поддерживает дедупликацию по содержимому и по идентификатору. Хэш считается после mapping, но до правил/webhooks; последующее редактирование записи его не меняет. Изменение mapping или исходных данных может изменить хэш. Для identifier-based режима нужен устойчивый идентификатор и одинаковое сопоставление колонок. [Duplicate detection](https://raw.githubusercontent.com/firefly-iii/docs/main/docs/docs/references/data-importer/duplicate-detection.md), Content-based / Identifier-based (строки 6–46).

**Наше предложение.** Хранить import_batch_id, источник, source_transaction_id (если действительно присутствует), отпечаток исходной строки и версию mapping. Не вычислять идентичность только из редактируемого комментария. Уникальность ограничить владельцем/источником/счётом согласно формату. При повторном импорте показывать added/skipped/ambiguous/error, а не одно «успешно». Это новая будущая функция, не найденная в архиве.

**Подтверждено документацией.** Mapping связывает входящие названия счетов/валют/категорий с существующими объектами. Пользователь может выбрать соответствие, а затем сохранить конфигурацию для следующего импорта. [How to map data](https://raw.githubusercontent.com/firefly-iii/docs/main/docs/docs/how-to/data-importer/import/map-data.md), What is mapping / How do I map data / Now what (строки 5–31).

**Наше предложение.** Использовать такой принцип при переходе от локальных cat-/acc-ID к серверным UUID (FE-06/07): предварительный отчёт соответствий, ручное разрешение неоднозначности, счётчики до/после. Схожее имя двух банковских счетов не доказательство идентичности. Сохранять только безопасную конфигурацию, не реальные выписки в Git.

**Подтверждено документацией.** Распознавание переводов требует корректного определения обоих счетов. Две записи одного перевода могут не объединиться при различиях в описании, идентификаторах или метаданных. Документация советует начинать с нескольких транзакций; применение правил после сохранения не повторяет автоматически дедупликацию. [How to import transfers](https://raw.githubusercontent.com/firefly-iii/docs/main/docs/docs/how-to/data-importer/import/transfers.md), Recognizing asset accounts / Transfers aren't merged (строки 4–43).

**Наше предложение.** Не обещать «ИИ автоматически разобрал все переводы». Добавить тест на два банковских экспорта с разными описаниями одного перевода; до подтверждения показать предполагаемую пару. Отдельно различать перевод между своими счетами и поступление от другого человека.

## 5. GnuCash: явный ввод валютного перевода

**Подтверждено документацией версии 5.** Диалог перевода использует сумму в валюте исходного счёта; при разных валютах принимает курс либо сумму получателя и рассчитывает другое значение. Пользователь завершает либо отменяет диалог. [Transfer Funds Dialog Box](https://www.gnucash.org/docs/v5/C/gnucash-manual/trans-win-enter.html), Basic Information / Currency Transfer / Finishing Up (строки 14–18,33–52).

**Наше предложение.** Если валютные переводы действительно понадобятся Алине, показывать обе суммы до записи. Пример синтетического теста: списано 9000 RUB, получено100 USD; нельзя создавать 9000 USD. Комиссия, курс фактической сделки и текущий оценочный курс — разные понятия, их контракт определить отдельно. Не требуется переносить весь бухгалтерский интерфейс GnuCash в Telegram.

## 6. Как организована разработка: документированные практики Actual

Это сведения из руководств разработчиков, а не вывод по внешнему виду приложения. Они подтверждают заявленный процесс, но мы не проверяли соблюдение каждого правила во всей истории проекта или последние CI runs. Прочитанный внешний AGENTS.md рассматривался только как материал исследования, его команды не выполнялись и его правила не применялись к AI Money.

1. **Небольшое изменение проходит проверку до review.** В официальном Development Workflow предусмотрены чтение текущей реализации, узкие изменения, typecheck, lint и профильные тесты. Крупную идею сначала обсуждают; PR сопровождается release note. [Contributing](https://actualbudget.org/docs/contributing/), Development Workflow и Submitting a Pull Request (строки 88–119). **Перенос в AI Money — предложение:** одна карточка аудита → один небольшой diff → тест ошибки и проверка исправления → запись пользовательского изменения. Команды Yarn из чужого проекта не переносить в наш npm/Python стек. Такой порядок удобен Алине: AI выдаёт проверяемую порцию работы вместо большой переписи.

2. **Формулы и пользовательский путь проверяются разными уровнями тестов.** Руководство описывает Vitest для unit tests, Playwright для E2E и отдельные визуальные проверки; рекомендует по возможности реальные реализации вместо чрезмерных mock. Для UI-изменений в checklist предусмотрены E2E. [Testing](https://actualbudget.org/docs/contributing/testing/), Testing Overview / Testing Best Practices / Visual Regression Tests / Testing Checklist (строки 38–44,126–177,225–232). **Перенос — предложение:** pytest для денег/БД, Vitest для parsing/клиента, короткий Playwright сценарий «создать→изменить→удалить перевод». Screenshot не доказывает правильность баланса. Не добавлять сложный monorepo task runner только потому, что он есть у Actual.

3. **Схема БД и API развиваются согласованно.** Руководство миграций связывает изменение схемы с обновлением API и AQL schema; советует осторожность при удалении таблиц/колонок из-за рисков возврата. [DB Migrations Guide](https://actualbudget.org/docs/contributing/project-details/migrations/), основной список (строки 40–51). **Перенос — предложение:** для A3 единая Alembic migration, совместимый контракт API/frontend и пробный upgrade старой копии с денежной сверкой. Сначала добавить и перенести данные, проверить, лишь затем планировать удаление старого. Это наше применение принципа, не требование использовать конкретную файловую схему миграций Actual.

Дополнительно открытый [AGENTS.md Actual](https://raw.githubusercontent.com/actualbudget/actual/master/AGENTS.md), Architecture & Package Structure / Testing Strategy, описывает отдельное платформонезависимое финансовое ядро и UI/API пакеты. Это поддерживает идею A7 отделить финансовые правила от экранов; не доказывает, что AI Money нужен такой же монорепозиторий или технология синхронизации.

# Банковский импорт: проверка доступности источников

Дата: 26.09.2026. Допущение: российские личные счета, исходя из банков в проекте; реальный банк Алины неизвестен. Применён deep-research. Никаких входов в банк, доступа к API клиентов или персональным данным не было.

## Рекомендация

Первый этап — импорт файла, который человек самостоятельно скачал из своего банка: предварительный просмотр → распознанные суммы/даты/валюта → поиск повторов → явное подтверждение. Поддержку конкретного банка обещать только после обезличенного образца актуальной выгрузки и регрессионных тестов. Автоматическое подключение банков пока отдельное исследование условий банка/партнёра.

## Выписка и товарный чек

Описанные банками документы отражают движения по счетам; доказательств выгрузки состава каждой покупки (товар, количество, цена) в них не найдено. Проектное следствие: строка «магазин, 1200 рублей» не позволяет достоверно разбить сумму на продукты/бытовую химию без товарного чека. Операции выписки и позиции чека — разные сущности. Нельзя обещать точную категоризацию товарных позиций по банковской строке или считать AI-догадку подтверждённым фактом.

## План приёмки импорта

1. Получить по одному обезличенному примеру реальной выгрузки нужных банков; сохранить формат, локаль и версию адаптера.
2. CSV/Excel обрабатывать детерминированно; PDF отдельным адаптером с обязательной сверкой итогов. AI может предложить категорию, но не менять сумму/валюту/дату без предупреждения.
3. Суммы хранить точно; различать дату операции и проводки, валюту счёта и операции, возвраты, комиссии, холды и финальные списания.
4. Повторная загрузка и пересекающиеся периоды не должны добавлять дубли; при отсутствии банковского transaction_id не склеивать автоматически одинаковые реальные покупки.
5. Перевод между своими счетами связывать в одну пару, исключая повторный доход/расход; импорт строки и ручная запись требуют механизма сопоставления.
6. Сверка: начальный остаток + проводки = конечный остаток в соответствующей валюте и по правилам данной выписки; расхождение останавливает автоматическое подтверждение.
7. Протоколировать парсер, файл/строку, решение о дубле и подтверждение; предусмотреть атомарный откат одной импортированной партии.

## Журнал поиска и пределы

Поиск: официальные tbank.ru/alfabank.ru, docs.ozon.ru/finance.ozon.ru, sberbank.ru и cbr.ru; отдельно retail против business.
