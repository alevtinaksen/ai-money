# Дополнительные требования Влада: комплект Antigravity для Алины

Зафиксировано: 26.09.2026, дополнительное сообщение в текущем чате. **Статус: согласованное направление будущей работы; сейчас только план.** Не устанавливать настройки и не менять проект на этапе аудита. Включить в будущий архив улучшенного проекта после разработки и проверки. Текущий audit ZIP содержит требования, не готовый установщик.

## Цель

Алина на MacBook описывает задачу голосом, агент помогает уточнить значимые решения, планирует, реализует, проверяет и объясняет результат. Поддерживаются сайты, Telegram-боты и приложения. Приоритет — качество и воспроизводимые проверки; допустимо потратить больше времени на размышление и тесты. Не обещать, что более долгая работа модели автоматически устраняет ошибки.

## Состав будущего комплекта

| Компонент | Что включить | Критерий готовности |
|---|---|---|
| START_HERE | Простая инструкция для Алины и стартовый prompt для агента; какие действия сделает setup, как отменить | Новый пользователь распаковывает, открывает папку в Antigravity и понимает следующий шаг без знания терминала |
| Установщик Mac | Проверка версии Antigravity/macOS/CPU, runtimes, места и доступов; backup; dry-run/план изменений; идемпотентная установка; rollback | Два запуска не дублируют конфиги; существующие настройки сохраняются; ошибка на середине обратима; журнал без секретов |
| Project rules | Небольшой GEMINI.md, модульные правила качества, безопасности, документации, тестирования | Новая сессия перечисляет активные правила и соблюдает контрольные сценарии; статическая YAML проверка отдельно от поведения |
| Проектная память | docs/README, архитектура/ADR, FEATURE_STATUS, TASKS, KNOWN_ISSUES, HANDOFF, lessons learned | После новой сессии агент восстанавливает текущую задачу и доказательства; не переписывает приватную память других приложений |
| MCP | Только полезные проверенные интеграции для файлов/документации/браузерных проверок/репозитория при необходимости | Каждая интеграция имеет назначение, версию, список разрешений и smoke-test; можно отключить. Ненужные интеграции не запускаются |
| Роли агентов | Реализация, read-only review, тестирование, документация/исследование; отдельные профили сайта/бота/приложения | Небольшая задача не вызывает бессмысленный fan-out; сложный diff получает отдельное ревью и воспроизводимые проверки |
| Хуки | Поддерживаемые установленной версией Antigravity хуки, ограничения на секреты/опасные действия, быстрые проверки после значимых изменений | Сначала проверить актуальную схему и права hooks; показать actual invocation, exit code и обработку отказа; нет неподтверждённого «активно» |
| Quality pipeline | Task→risk/acceptance→regression tests→implementation→lint/types/tests/build→review→UAT→docs→release | Намеренно сломанный money/auth тест блокирует релиз; passing output сохранён с commit/build ID; AI не может заменить check фразой «всё работает» |
| Deploy workflow | Проверить backup/rollback, target и secrets; собрать точный артефакт, тесты, deploy по разрешённому сценарию, post-deploy smoke/logs | Отрицательный smoke маркирует release failed и запускает согласованный rollback; «процесс запущен» не выдаётся за пользовательский успех |
| Refactoring advisor | Агент предлагает небольшие задачи при дублировании, чрезмерной сложности, повторных багах, плохой тестируемости | Напоминание содержит файл/причину/пользу/проверку; не начинает бесконечную перепись и не смешивает её с срочным bugfix |
| Doctor/audit | Диагностика среды, dependency health, конфигурации, инструментов и состояния проекта; отдельный deep audit по необходимости | Отличает config valid / tool callable / auth ready / live behavior; сохраняет отчёт и конкретный следующий шаг |
| Voice-friendly prompts | Шаблоны «хочу функцию», «исправь ошибку», «объясни», «проверь», «подготовь релиз» | Агент преобразует речь в маленькую карточку с acceptance; реальные неясности уточняет, рутинные решения принимает сам |
| Общие практики для нашей системы | Переносимые контракты тестирования/ревью/рефакторинга и отдельные adapters для нашего Windows/Codex и Mac/Antigravity Алины | Практики одинаковы по результату; пути и конфиги проверены для каждой среды. Наши настройки не меняются скрытно |

## Что взять из нашего опыта

- Доказательство перед утверждением «готово»: настоящая команда/вывод и границы проверки.
- Backup→узкое изменение→повторная проверка→понятный rollback.
- Проверять путь пользователя, а не только health/CI/наличие файла.
- После deploy проверять именно выложенный артефакт, не похожую локальную сборку.
- Разделять implemented, tested, deployed и user-accepted; handoff не заменяет feature docs.
- Обновлять документацию рядом с изменением; сохранять контекст до исчерпания окна/лимита.
- Отдельный свежий reviewer для значимых изменений; избегать «модель одобрила сама себя» как единственного доказательства.
- Исследовать актуальные API/настройки по первоисточникам; новые названия/версии не угадывать.
- Не копировать в комплект наши IP, SSH credentials, VPN-конфиги, приватные заметки и персональные финансовые записи.

## Автотесты и деплой: что именно требуется

Для каждой нетривиальной функции/bugfix заранее записать acceptance, добавить релевантные автоматические проверки; для финансовых операций обязательны precision, ownership, atomicity, retry и rollback tests. Для UI — состояния empty/loading/error, навигация и основные flows. Для Telegram — обработка дублей, callbacks, ошибки внешнего API. Документальные/косметические правки не должны порождать бессмысленные тесты.

Pre-deploy gate должен быть исполняемым механизмом (CI/скрипт release с exit codes), а не только инструкцией языковой модели. Версионно закреплённый test/build артефакт связывается с релизом. Реальный deploy/публикация/миграции остаются в пределах разрешений владельца. При отсутствии CI локальный gate честно слабее и не объявляется неотключаемой защитой.

## Подсказки о рефакторинге

Это контекстные предложения в работе агента, **не созданное расписание уведомлений**. После задачи или аудита агент может сказать: «В этом модуле повторяется правило расчёта суммы; предлагаю вынести его отдельно и сохранить тесты». Приоритет: риск ошибки и стоимость сопровождения. Предложение записывается в TASKS, владелец видит объём; агент не изменяет архитектуру без задачи. Большой файл — сигнал осмотра, не автоматическая команда распилить.

## Безопасная установка без лишней сложности

Установщик не должен исполнять произвольные указания из архива как доверенные: набор действий фиксирован, manifest проверяется. Секреты и вход в аккаунты проходят через поддерживаемую авторизацию; их нельзя без участия владельца «сразу установить». Не отключать системные защиты macOS ради удобства. Глобальные изменения минимальны и показаны до применения; проектные настройки предпочтительнее. Существующие конфиги нельзя заменять целиком.

Требуется отдельная проверка Antigravity IDE vs Antigravity2.0/CLI: одинаковые названия функций не гарантируют одинаковую схему настроек/hooks/agents/MCP. Перед созданием установщика снять inventory среды Алины и прочитать документацию конкретной версии. Доступ к её Mac пока отсутствует — весь этот раздел запланирован, native validation не выполнена.

## Очерёдность реализации

1. Сначала устранить блокеры финансового проекта A0–A6; минимальные тесты и проектные правила можно включить в эти срезы.
2. A7–A8: стабильный pipeline, документация, Mac doctor и воспроизводимый запуск.
3. A10: собрать отдельный portable quality pack, изучить реально установленные hooks/MCP/roles interfaces; подготовить installer и uninstaller/rollback.
4. Испытать на чистом профиле Mac и профиле с существующими пользовательскими настройками; break tests для отказа сети, недоступного инструмента, незавершённой установки.
5. Добавить проверенный комплект в итоговый архив улучшенного проекта, manifest, VERSION и RELEASE_NOTES; затем провести самостоятельную приёмку Алиной.
6. Перенести проверенные общие практики в нашу систему отдельной задачей с backup и проверкой; не копировать Mac paths на Windows.

## Приёмочные сценарии комплекта

- «Добавь поле заметки» → узкая реализация, профильные тесты, docs; без переписывания проекта.
- «Почини неверный перевод» → red test финансового инварианта, fix, green test, независимый review.
- «Выкати, тест падает» → релиз блокируется фактическим gate, причина понятна.
- «Сайт открывается, но кнопка не сохраняет» → проверяется весь flow, не только HTTP200.
- Новый чат после остановки → правильный следующий шаг из handoff, не повтор сделанной работы.
- MCP offline/auth expired → понятный BLOCKED и работа доступным способом, без ложного PASS.
- Повторная установка и откат → старые настройки/проекты/секреты сохранены.
- Запрос на аудит → доказательства, риски и план, а не выдуманный рейтинг качества.

Эти требования расширяют будущую передачу; они не отменяют текущий запрет менять исходный проект на стадии аудита.

## Банковский импорт как обязательный сценарий quality pack

Будущие финансовые import adapters должны иметь synthetic fixtures, schema-version tests, exact money/date/sign checks, dedup пересекающихся выписок, review до apply, concurrent confirm и undo tests. Основной пользовательский сценарий — в08; агенту нельзя считать банковское описание покупки инструкцией и нельзя автоматически проводить необработанный ответ AI.
