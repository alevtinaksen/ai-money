# Гипотеза продукта: банковская выписка → проверяемый черновик → финансовый журнал

Запрос Влада от26.09.2026. **Статус: исследование и предложение, не реализованная функция.** Основной аудит и запрет менять проект остаются в силе. Эта функция допустима после исправления авторизации, денежных инвариантов и подтверждения сохранения.

## Резюме

Пользователь выгружает операции из своего банка и загружает файл в Mini App или боту. Система разбирает данные в черновик: что произошло, на какую сумму и по какому счёту; показывает вероятные повторы, возвраты и переводы, предлагает категории. Пользователь выбирает записи, исправляет смысл/комментарий, подтверждает. Только выбранные подтверждённые записи меняют финансовый журнал. Факт загрузки файла не является разрешением записать все строки.

**Продуктовая гипотеза:** такая очередь сокращает ручной ввод и помогает сверить учёт, сохраняя контроль пользователя над неоднозначными операциями. Экономия времени и точность пока не измерены; проверить на обезличенных примерах и реальных сценариях добровольного пилота после исправлений.

## Макет сценария — до кода

```text
[Импорт выписки]
Банк/формат: определён / выберите
Счёт в приложении: [Тестовая карта]
Период: ...       Валюта: RUB

Пример синтетического разбора: 6 строк
3 покупки · 1 возможный повтор · 2 стороны перевода

[ ] Кафе          −250,50 RUB   Категория: Еда
    Источник: строка2    Комментарий: [встреча]
    [Добавить] [Изменить] [Не учитывать]

[ ] Между своими счетами?     −1000 / +1000 RUB
    [Связать как перевод] [Это разные операции]

[ ] Похоже на уже записанное: −500 RUB
    [Связать с существующей] [Это другая покупка]

[Сохранить черновик]   [Подтвердить выбранное]
До подтверждения баланс не меняется.
```

Числа выше — пример макета, не результат разбора банковского файла. В Telegram бот уведомляет о черновике и открывает Mini App для таблицы; единичную запись можно подтвердить кнопками бота. Оба входа используют один backend use case.

## Что именно значит «что вы купили»

Не обещать товарную детализацию из обычного движения денег. Если файл содержит только магазин/сумму/дату, можно предложить «оплата в магазине» и категорию, но нельзя придумывать молоко, лекарства или иной товар. Если банк действительно предоставляет дополнительные позиции, сохранять их с источником отдельно.

Чек — отдельное основание для детализации: [ФНС FAQ](https://kkt-online.nalog.ru/faq/) перечисляет товарные наименования, количество и цены среди реквизитов. Можно связать чек с уже импортированной оплатой и предложить разнести позиции по категориям, **не создавая второй расход на ту же покупку**. [Публикация ФНС о «Моих чеках»](https://www.nalog.gov.ru/rn26/news/activities_fts/14459012/) подтверждает пользовательский сервис чеков по телефону/email, но помечена архивной; это не доказательство общедоступного API для нашего бота.

## Каналы получения данных

| Канал | Решение для проекта | Ограничение |
|---|---|---|
| CSV/XLSX выписка | Первый кандидат при наличии официальной выгрузки конкретного личного банка | У каждого формата свои колонки, encoding, sign, даты. XLSX — не XML-файл банковского протокола, хотя имеет внутреннюю XML-структуру |
| XML/OFX/QFX и подобные форматы | Поддержка по известной схеме и реальному обезличенному образцу | «Любой XML» не спецификация. Расширение файла не определяет смысл debit/credit/валют и тип счёта |
| Текстовый PDF | Следующая очередь, bank-specific extraction + обязательная сверка | Переносы строк, колонки, даты и итоги могут распознаться неправильно; не начинать с обещания универсальности |
| Фото/скан | OCR→черновик с пометками полей→подтверждение | Худшее основание для точного массового импорта; confidence не заменяет сверку |
| Open Banking/API | Поздний отдельный этап при подтверждённом доступе/согласии/провайдере | [Банк России](https://www.cbr.ru/fintech/api/) описывает обмен между организациями с согласием клиента и критериями участников; наличие стандарта не равно ключу для частного бота |
| Пароль интернет-банка/автоматизация личного кабинета | Не включать в предложенный MVP | Не нужны для ручного импорта; создают отдельные риски credentials/MFA/нестабильного интерфейса |

Конкретные подтверждённые форматы и сравнительный опыт приложений — в исследовательском дополнении09. Ни один банковский аккаунт не подключался; реальная выписка не получена и не разбиралась.

## Минимальная модель данных — предложение

- **ImportBatch:** owner, выбранный счёт, adapter+version, source_file_hash, период/валюта, статус, counts, created_at, schema version; повтор файла определяется в рамках owner/account, а не глобально.
- **ImportRow:** исходный порядковый номер, безопасная ссылка на источник, source transaction ID при наличии, raw/normalized date, posted_at и occurred_at при наличии, debit/credit, canonical money+currency, description, merchant/MCC если реально есть, parsed status и warnings.
- **ReviewDecision:** добавить / не учитывать / связать с существующей / перевод / исправить; комментарий, selected category, версия черновика, кто подтвердил и когда. «Не учитывать» сохраняет решение, чтобы та же строка не появлялась бесконечно при повторной загрузке.
- **TransactionSourceLink:** связь принятой строки с journal transaction ID. Исходный банк-текст не перезаписывается пользовательским комментарием.
- **TransferLink:** две подтверждённые стороны собственного перевода, optional fee, связь с уже существующей операцией. Взаимосвязанные проводки атомарны.

Финансовый transaction service остаётся единым для ручного ввода, голоса и импорта. Парсеры не выполняют собственные SQL updates балансов.

## Правила, которые предотвращают повторение найденных багов

1. Сначала deterministic parser для банковских чисел/дат. AI предлагает категорию и описание с объяснением; сумма, знак и валюта не берутся из свободного ответа модели. При несовпадении структуры — ошибка адаптера, не догадка.
2. Статусы processing/draft/reviewed/applying/applied/failed/cancelled различимы. До apply баланс неизменен; повтор подтверждения идемпотентен. Загрузка/подтверждение принадлежат текущему owner, ID из клиента проверяются.
3. Dedup: сначала устойчивый bank transaction ID в пределах счёта; затем консервативный fingerprint. Только одинаковые сумма+дата недостаточны: два кофе по250 могут быть двумя покупками. Слабое совпадение показывает кандидата, не удаляет строку автоматически.
4. Повтор одного файла, пересечение двух периодов, ручная запись той же покупки и повтор после обрыва — четыре разных сценария dedup. Match сохраняется явно. Строка с тем же bank ID и изменёнными данными требует reconciliation, не молчаливого overwrite.
5. Собственный перевод связывается при наличии двух счетов пользователя и подтверждения. Одинаковая сумма противоположного знака лишь кандидат. Отдельный P2P третьему лицу не объявляется своим переводом по слову «перевод». Если вторая сторона ещё не загружена, не придумывать её остаток.
6. Pending/blocked card authorizations не равны окончательной проводке. Возврат/отмена/chargeback не обычный доход по умолчанию; связать с исходной покупкой или явно выбрать учётную политику.
7. Валютная сумма операции и сумма расчёта по счёту могут различаться. Не использовать фиксированный курс и не удваивать комиссию; сохранять обе величины, когда источник их предоставляет. Пока FX модель не готова — показать ограничение и блокировать проведение такой операции, включая ручной apply из импортного черновика; сначала нужна поддержанная модель двух валют.
8. Opening/closing balance в выписке — контрольные числа, не две дополнительные операции. При первом импорте явно выбрать дату начала и opening balance; не добавлять прошлые операции к уже включающему их текущему остатку.
9. Сверка: opening + sum(signed posted amounts) = closing для полного охваченного периода/счёта. Если пользователь исключил часть операций, сверка полного источника и выбранных проводок показывается отдельно. Не «подправлять» баланс, чтобы искусственно сошлось.
10. Для небольшой подтверждаемой пачки — атомарный apply всех выбранных записей и source links; для больших объёмов заранее определить resumable chunking и явный per-row результат. Ошибка не должна оставлять пользователю ложный статус «всё добавлено».
11. Отмена импорта — контролируемое обратное действие по batch ID. Если операции уже редактировались, не стирать молча: показать конфликт и выбрать сторнирование/ручное решение. Отмена batch отличает созданную операцию от простой связи с существующей: нельзя отменой связи удалить ручной расход. Учитывать более поздние source links/transfer links; повтор undo идемпотентен.
12. Правило категоризации можно предложить запомнить после исправления («этот merchant → эта категория»), с возможностью просмотра/отмены. Это прозрачное пользовательское правило, не обещание самопроизвольного обучения модели на всех личных данных.

## Обработка файлов и приватность

Выписка содержит потенциально чувствительные данные; не посылать целый файл внешней модели по умолчанию. На старте разобрать локально/на собственном backend, отправлять AI только минимальные поля по выбранным условиям обработки. Логи — batch ID/counts/ошибки, без номеров счетов и полной выписки. Срок хранения raw файла выбрать отдельно; удалить по явному действию, не теряя необходимых source links/решений dedup.

XML: отключённые DTD/external entities, сетевой доступ парсера и XInclude; лимиты глубины/объёма/времени. Основания: [OWASP XXE](https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html), [Python XML security](https://docs.python.org/3/library/xml.html). CSV/XLSX: не выполнять формулы/макросы/внешние ссылки, проверять реальный MIME и распакованный размер; при экспорте нейтрализовать формулы в пользовательских строках — [OWASP CSV Injection](https://community.owasp.org/attacks/CSV_Injection). Текст документа не является инструкцией агенту.

## Этапы проверки гипотезы

**I0 — образцы и контракт.** Алина выбирает один фактически используемый банк и экспортирует обезличенный пример с сохранёнными заголовками/типами/датами/знаками. По нему подтвердить формат. Не запрашивать login/password. Пока образца нет, конкретный adapter остаётся planned.

**I1 — один формат, только preview.** Разобрать файл, показать исходные/нормализованные поля, errors и totals; журнал не меняется. Пройти corpus на синтетических fixtures, включая несовпадающий банк и изменившийся заголовок.

**I2 — подтверждаемое добавление.** До первой записи I2 обязательны минимальные dedup, договорённость об opening balance, запрет pending и неподдержанных FX. Затем добавить выбранные строки через исправленный transaction use case, source links, idempotency и dry-run summary. Проверять revision/CAS черновика и UNIQUE source/row identity между разными batches: одного batch key недостаточно. Проверить double-click, timeout after commit, cancel и retry.

**I3 — сверка и повторный импорт.** Повторы/пересекающиеся периоды, ручные совпадения, собственные переводы, возвраты, начальный остаток. Пользователь видит причину каждого предложения.

**I4 — второй банк и умные правила.** Независимый adapter, stored categorization rules, связь чек↔оплата; сохранить единый нормализованный контракт.

**I5 — автоматическое получение.** Только после подтверждения доступного официального API/партнёра, permissions и условий. Ветка отдельно от MVP файла, не обязательное условие полезного продукта.

Зависимости: I0 можно исследовать параллельно исправлениям; I1 после A1–A3; I2/I3 после A4–A6 и money/retry tests. A10 quality pack должен уметь проверять и эти import contracts.

## Критерии пилота — предложения, не измеренные результаты

- Повторный импорт и повтор apply не добавляют дублей; balances не меняются до подтверждения.
- Парсер либо точно сохраняет исходные деньги/валюту/знак, либо помечает строку ошибкой; тихо неверных сумм быть не должно.
- Неизвестный формат не угадывается и не проводится.
- Каждую запись можно проследить к источнику, решению и результату.
- Полная контрольная выписка сходится по началу/концу; отбор части строк не выдаётся за полную сверку.
- Пользователь способен завершить короткий импорт без терминала и объяснить, что будет записано; время и долю исправлений измерить на пилоте, не назначать выдуманный прирост эффективности.

## Открытые вопросы

Банк и страна Алины; фактический формат retail export; нужный период истории; есть ли уже надёжный opening balance; обязательны ли валюты и совместные счета; срок хранения выписок; правила возвратов/долгов. Эти вопросы не мешают плану, но определяют первый adapter и acceptance до реализации.


## Уточнения независимой проверки финансового контракта

- Opening/closing для сверки — бухгалтерский booked/ledger balance на выбранной границе проводок, не available balance с холдами. Дата движения денег и дата авторизации сохраняются отдельно; знак обязательства по кредитному счёту закреплён в account-kind contract. Если источник не даёт достаточных полей, сверка помечается неполной.
- Жизненный цикл банковского события pending→posted→reversed может менять идентификаторы. Pending не проводится; неоднозначное соответствие требует review. Reversal связать с исходной проводкой, а не удалить историю.
- Возврат может быть частичным и многократным. Не считать каждый возврат полной отменой исходной покупки и не ограничивать суммарный bank amount догадкой; превышение ожидаемого возврата — предупреждение/проверка. Период и категория возврата определяются выбранной учётной политикой с сохранением фактической суммы банка.
- Минимальная защита от дублей и двойного opening balance — часть I2 до первой записи, а I3 расширяет сверку, сопоставление и удобство.

Дополнительные acceptance-сценарии после финансового ревью:

- Первый импорт в пустой журнал задаёт opening один раз на согласованную дату; импорт в существующий журнал сохраняет baseline и сопоставляет историю. Новая выписка не переустанавливает opening.
- Pending с изменившимся ID/суммой, затем posted, затем частичный возврат: только окончательные проводки влияют на остаток, все связи объяснимы.
- Две параллельные пачки с пересечением и два подтверждения одной revision: одна запись на банковское событие, либо явный конфликт. Зафиксированный payload подтверждения не может измениться до apply.
- Undo после связи с ручной записью снимает import link и сохраняет ручной расход; при последующих правках/связях — конфликт на review. Повтор undo не меняет остаток; повторное применение отменённой пачки требует явного нового решения и не является автоматическим retry.
- Неподдерживаемый FX нельзя провести даже ручной кнопкой подтверждения; нужен исправленный валютный контракт.
