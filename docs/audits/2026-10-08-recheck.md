### R01. Потеря идентификатора незавершённого ручного расхода

**Воспроизведение:** открыть App → создать расход 10 → сервер успевает сохранить его, но ответ задержан → нажать внутреннюю кнопку «Закрыть» → доставка ответа завершается сетевой ошибкой → снова открыть форму и повторить расход 10.

**Наблюдаемое:** настоящий тестовый HTTP API сохраняет две операции по 10; баланс отдельного счёта становится **1000 → 980**. Ожидается 990 при повторе одной незавершённой записи. Потеря ответа моделируется только после настоящего HTTP200/commit; последующие GET подтверждают реальные записи и остаток SQLite.

Внешний Dialog блокирует закрытие при `ledger.busy` (`App.tsx:133`), но внутренний `onClose` в строке136 обходит эту проверку. `TransactionEditor.tsx:34` вызывает его без учёта `saving`. При повторном открытии `AddTransactionScreen` получает новый `client_id` (`:49`, `:273–275`); сервер корректно воспринимает его как другую операцию.

**Минимальное исправление:** использовать единый проверяемый обработчик закрытия для всех кнопок и Escape; сохранять payload/client_id незавершённого черновика до подтверждённого результата или сверки с сервером. Одного disabled на кнопке Save недостаточно. Регрессия: commit → потеря ответа → закрытие/повтор → одна запись и один расход.

**Доказательство:** [HTTP/SQLite результат](../../work/audit-recheck-2026-10-08/frontend/live-retry-evidence.json), [runtime test](../../work/audit-recheck-2026-10-08/frontend/live-retry.test.tsx), [лог](../../work/audit-recheck-2026-10-08/frontend/live-retry.log).

### R02. Повторное AI-распознавание уничтожает сохраняемую строку

**Воспроизведение:** текст «кофе10» → предложение → «Подтвердить и сохранить» → настоящий POST уже сохранён, ответ задержан → ещё раз «Подготовить черновик» → потеря первого ответа → подтверждение нового предложения.

**Наблюдаемое:** отдельный synthetic счёт **1000 → 980**, две операции10. Ожидается сохранение исходного незавершённого предложения и его идентификатора, чтобы повтор запроса не изменял деньги второй раз. Облачный AI для воспроизведения не нужен: используется настоящий локальный `/api/ai/parse-text`.

`AiPreview.tsx:17` очищает result и размонтирует ProposalRow; управление распознаванием (`:26`, `:31`) знает только о loading распознавания, не о сохранении строк. Идентификатор живёт внутри заменяемой строки (`ProposalRow.tsx:18`, `:30–33`), поэтому новая строка имеет другой ключ.

**Минимальное исправление:** поднять состояние записи и идентификаторы строк выше заменяемого результата распознавания; запрещать повторное распознавание, замену файла и закрытие, пока запись не завершена; сохранять неопределённый результат для безопасного повтора. Регрессия отдельная от R01, потому что повторное распознавание возможно без закрытия окна.

**Доказательство:** [HTTP/SQLite результат](../../work/audit-recheck-2026-10-08/frontend/live-ai-retry-evidence.json), [runtime test](../../work/audit-recheck-2026-10-08/frontend/live-ai-retry.test.tsx), [лог](../../work/audit-recheck-2026-10-08/frontend/live-ai-retry.log).

### R03. Дизайн-сервер может отдавать приватные файлы

**Воспроизведение на безопасной копии:** тот же Handler запускается поверх временного каталога, в котором `.env` и внешний файл содержат только synthetic заглушки. `GET /bot/.env` возвращает200 и содержимое заглушки. `GET /preview/../../outside.txt` также возвращает200, выходя за папку проекта-заглушки.

**Наблюдаемое:** fallback `super().translate_path` (`preview/server.py:33`) обслуживает рабочий каталог; ручные пути `:21–31` не проверяют итоговый resolved path. Каждый ответ получает `Access-Control-Allow-Origin: *` (`:37`). Ожидается обслуживание исключительно разрешённых публичных артефактов, запрет обхода каталога и отсутствие wildcard CORS.

**Влияние:** при запуске `Start_Design_Stand.command` из корня в HTTP-область попадают файлы проекта; потенциально это `.env`, финансовая БД и `.git`. Loopback снижает доступность из сети, но не делает такие файлы публичными. Фактическая утечка настоящих ключей не проверялась и не утверждается; чтение из стороннего сайта может дополнительно ограничиваться защитой конкретного браузера. HTTP-чтение файлов доказано.

**Минимальное исправление:** allowlist маршрутов для preview/dist, проверка `resolve()` и принадлежности разрешённому корню, запрет directory listing и symlink escape, удаление wildcard CORS. Добавить regression чтения synthetic `.env`, traversal и symlink. До исправления использовать обычный контролируемый Vite-превью вместо этого файлового сервера.

**Доказательство:** [probe](../../work/audit-recheck-2026-10-08/root/preview_probe.py), [результат](../../work/audit-recheck-2026-10-08/root/preview-result.json). Настоящие секреты не читались и не выводились.

### R04. Изменение имени счёта ломает чтение списка

**Воспроизведение:** создать корректный счёт → `PUT /api/accounts/{id}` с `name:""` или именем из101 символа → `GET /api/accounts`. Длинное имя также можно ввести в редакторе: поле не имеет maxLength.

**Наблюдаемое:** PUT отвечает400, хотя новое имя уже сохранено в SQLite. Следующий GET всего списка тоже400. Ожидается отклонение недопустимого имени до изменения БД, исходное имя и рабочий список сохраняются.

`AccountUpdate.name` (`schemas/finance.py:46`) не имеет ограничений, которые есть у `AccountBase` (`:30`). Service commit (`finance_svc.py:101`) предшествует проверке AccountResponse (`api/routes/accounts.py:43`); чтение списка проверяет каждую запись (`:19`) и падает целиком. Поскольку `useLedger.refresh` объединяет ответы, проблема одного счёта мешает загрузить финансовый снимок пользователя.

**Минимальное исправление:** единый контракт имени при create/update, валидация до commit, HTTP regression неверного PUT с последующим успешным GET. UI-ограничение полезно, но не заменяет API-валидацию.

**Доказательство:** [probe](../../work/audit-recheck-2026-10-08/backend/probe.py), [result.json](../../work/audit-recheck-2026-10-08/backend/result.json), записи `account_name_empty` / `account_name_too_long`.

### R05. Редактор незаметно удаляет комментарий

**Воспроизведение:** операция с категорией «Еда» и настоящим сохранённым `note="Еда"` → открыть редактор → изменить только сумму10 на11 → сохранить.

**Наблюдаемое:** поле комментария инициализируется пустой строкой, вызывается `onSave` с `note:null`; ожидается сохранение нетронутого комментария. Форматтер для краткой подписи (`EditTransactionModal.tsx:502–503`) используется как источник редактируемых данных (`:554–555`, `:579–586`), а затем отправляется на сервер (`:665`). Это особенно легко встретить: новая ручная операция без комментария сама записывает название категории в note (`AddTransactionScreen.tsx:256–259`).

**Минимальное исправление:** инициализировать редактор сырым `transaction.note`; визуальную очистку подписи применять только в списке. Regression изменения суммы без изменения заметки.

**Доказательство:** contract probe в [contracts.test.tsx](../../work/audit-recheck-2026-10-08/frontend/contracts.test.tsx), [лог](../../work/audit-recheck-2026-10-08/frontend/probes.log). Здесь проверен фактический payload компонента; отдельный HTTP roundtrip именно этого дефекта не выполнялся.

### R06. Архивирование закрывает редактирование исторических заметок

**Воспроизведение:** создать расход → архивировать его категорию; отдельно повторить со счётом → PUT операции с текущей revision и только новым note.

**Наблюдаемое:**400 «Категория не найдена или не подходит…» / «Счёт не найден или архивирован», история читается. Ожидается возможность исправить описание без изменения денег и исторических ссылок. `update_transaction` (`finance_transactions.py:170`) использует ту же проверку active references (`:24–39`), что и создание новых операций.

**Минимальное исправление:** допускать неизменённые принадлежащие владельцу архивные ссылки при правке метаданных. Политику финансовых изменений архивной операции следует явно закрепить; запрет новых операций на архивном счёте сохранить. Регрессии отдельно для note-only и смены ссылки.

**Доказательство:** backend probe/result.json, случаи `archived_category_note_edit` и `archived_account_note_edit`. Это подтверждённое ограничение текущего редактирования; потери истории или денег в данном сценарии не обнаружено.

### R07. Параллельные изменения создают цикл категорий

**Воспроизведение:** две независимые SQLite sessions одновременно меняют родителей A→B и B→A. Barrier в probe фиксирует допустимое расписание, когда обе проверки читают первоначальное состояние до записи; продукт не подменяется.

**Наблюдаемое:** обе операции commit, сохраняется A↔B. Архивирование блокируется активным дочерним объектом. Ожидается отклонение одной операции и ацикличная структура. В `finance_svc.py:147–159` проверка графа и запись не защищены от изменений другого клиента.

**Минимальное исправление:** сериализовать чтение и изменение иерархии одного владельца в БД; для SQLite захватывать write transaction до проверки, для PostgreSQL применять подходящую блокировку владельца. Revision только на изменяемой категории не предотвращает конфликт между двумя разными узлами.

**Доказательство:** [probe](../../work/audit-recheck-2026-10-08/backend/concurrency_probe.py), [результат](../../work/audit-recheck-2026-10-08/backend/concurrency_result.json). PostgreSQL не проверен.

### R08. Транскрипция Groq обходит общий cloud limiter

**Воспроизведение:** шесть параллельных `parse_media(audio/ogg)` с замоканным HTTP adapter и synthetic ключом, без сети.

**Наблюдаемое:** peak concurrent transcription=6, generation=4. Ожидается заявленный в `docs/features/ai-and-bot.md` cap4 для внешних вызовов. `ai_provider.py:38–43` не приобретает слот; вызов транскрипции происходит раньше защищённой генерации (`ai_parser.py:245–247`).

**Влияние:** нагрузка голосовых запросов обходит cap и увеличивает риск provider429 и timeout. Ограничение10 запросов в минуту на пользователя не задаёт общий максимум параллельных вызовов.

**Минимальное исправление:** единый limiter для каждого отдельного внешнего вызова с bounded wait. Не захватывать его дважды вложенно для всего pipeline и генерации, чтобы не создать deadlock.

**Доказательство:** [probe](../../work/audit-recheck-2026-10-08/backend/cloud_slots_probe.py), [результат](../../work/audit-recheck-2026-10-08/backend/cloud_slots_result.json). Реальные облачные квоты и latency не тестировались.

### R09. Dist в дизайн-стенде не подключён к API

**Воспроизведение:** подготовленный dist → сервер `preview/server.py` → открыть `/preview/index.html` → «AI Money (Релиз dist)» → «Войти локально». Проверено в браузере над копией только публичных артефактов, с тем же Handler.

**Наблюдаемое:** UI показывает ошибку локального входа; POST `/api/auth/local` получает501, потому что сервер обслуживает только файлы. Путь `/fonts/JetBrainsMono-Regular.woff2` получает404. iframe (`preview/index.html:609`) направлен на этот origin, поэтому относительный `/api` попадает в файловый сервер; публичные ресурсы dist вне `/assets` не маршрутизированы. Надпись стенда «Подключено (Live)» не подтверждается рабочим входом.

**Ожидаемое:** документированный запуск должен открывать рабочее приложение через API или ясно обозначенный самостоятельный synthetic mock. Экраны не должны зависеть от случайно запущенного соседнего сервиса. Основной путь `scripts/project.py backend/frontend` работает и этим дефектом не отменяется.

**Минимальное исправление:** направлять iframe на согласованный работающий app origin либо добавить узкий loopback API proxy и корректную раздачу публичных ресурсов. Это делать вместе с R03, чтобы не расширять опасный fallback. Переходы стенда через hash (`preview/index.html:844`) также не связаны со state-навигацией App; требуется отдельный контракт сценариев, если стенд должен ими управлять.

**Доказательство:** [снимок ошибки](../../work/audit-recheck-2026-10-08/root/stand-login-error.png); actual Handler/browser POST501 и font404; [безопасный запуск копии](../../work/audit-recheck-2026-10-08/root/serve_preview_fixture.py).

## Архитектура и тестовая защита

Финансовое ядро использует целые копейки, общие сервисы для API/бота, атомарные SQL-изменения остатков, revision для изменения/удаления и unique client_id для создания. Тесты покрывают owner isolation, rollback перевода, точность денег, валюты, UTC, импорты и SQLite concurrency. Эти механизмы стоит сохранить.

Основные оставшиеся разрывы находятся между UI-состоянием и подтверждением сервера, а также между входной и выходной схемой. Имеющиеся тесты подтверждают retry пока компонент не заменён; они не покрывали закрытие/reparse после commit с потерянным ответом. Stand в `preview/` не входит в Ruff/structure scan текущего quality и не имеет runtime acceptance, поэтому зелёная проверка не охватывает R03/R09.

Пять документированных исключений размеров проходят gate. Редактор721 строк и история515 строк остаются областями повышенной стоимости сопровождения; это технический долг, а не самостоятельный runtime-баг. Неиспользуемый CategoryDetail и legacy parser не считать реализованными пользовательскими возможностями. Массовый рефакторинг перед исправлением P1 не нужен.

Опровергнуто отдельным пробным запуском: concurrent double tap создания счёта через полный App делает один POST благодаря `writing.current` в useLedger. Экспорт явно назван экспортом старых локальных черновиков; отсутствие серверного экспорта — возможная следующая функция, а не ложный экспорт текущих данных.

## Рекомендуемый порядок

1. **R01/R02: незавершённые записи.** Один узкий этап с regression commit/lost-response для ручной формы и AI; удержание ключа запроса и единое блокирование заменяющих действий. Ориентир3–6 часов, включая проверки; предотвращает неверный бюджет.
2. **R03/R04: файлы стенда и контракт счёта.** Allowlist server, traversal tests; Field constraints и HTTP rollback regression. Ориентир2–4 часа. До R03 не запускать текущий файловый стенд над папкой с настоящей БД/ключами.
3. **R05/R06: безопасное редактирование истории.** Raw note и явно описанная политика архивных ссылок. Ориентир2–4 часа; финансовые ссылки не менять автоматически.
4. **R07/R08/R09: конкуренция и стенд.** Блокировка графа, общий cloud limiter, согласованный app origin/сценарии. Ориентир4–8 часов; PostgreSQL и облачная приёмка потребуют отдельных окружений.
5. После этого — общий quality и отдельная приёмка физического Telegram на synthetic данных. Деплой, push и работа с настоящими финансовыми данными не выполнялись и этим аудитом не авторизуются.

Оценки — рабочие диапазоны для планирования, без ожидания внешних доступов; они не гарантируют срок.
