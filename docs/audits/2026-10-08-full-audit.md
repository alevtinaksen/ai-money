# AI Money: полный локальный аудит 2026-10-08

Проверено main / 7c1d37c, macOS, Python 3.12.14, Node 25.9.0, Vite 6.4.3. Аудит охватывает frontend, HTTP API, финансовые сервисы, Telegram flow, AI, импорт, backup/restore, запуск и quality gates. Продуктовые исходники не изменены, production не изменялся. Пользовательские изменения сохранены.

**Вывод: текущая версия не готова для доверенного учёта реальных финансов.** Серверное ядро имеет полезные гарантии целых копеек, владельца, атомарности и версий, но frontend ведёт независимую книгу, скрывает отказы и не соблюдает контракт сервера. Безопасность webhook и согласие на внешнее AI имеют подтверждённые дефекты. Зелёный quality не означает проверенное поведение.

P1 — существенный сбой, повреждение учёта или нарушение доступа/согласия; P2 — обычный дефект. P0 не установлен. Ниже перечислены отдельные причины, а не независимые «все возможные ошибки».

## Подтверждённые находки

### A01 — P1: webhook разрешает подменять Telegram sender

**Место:** `bot/app/main.py:169`, `bot/app/core/config.py:29`.
**Триггер:** бот запущен, TELEGRAM_WEBHOOK_SECRET не задан; POST синтетического Update с произвольным from.id.
**Наблюдение:** локальный ASGI/mock dispatcher: HTTP 200, feed_update=1 без Telegram-auth. Проверка заголовка существует только при непустом секрете; маршрут доступен и при polling. Бот доверяет from_user.id.
**Ожидание/влияние:** только Telegram должен доставлять события. Можно инициировать бот-действия от чужого ID; подтверждение чужого черновика дополнительно требует знать его UUID. Захват произвольного неизвестного черновика не доказан.
**Исправление:** отдельный явный webhook mode, обязательный секрет до старта, endpoint закрыт вне режима; не отдавать `str(exc)` клиенту (`main.py:181`).

### A02 — P1: provider=disabled и consent=false обходятся

**Место:** `bot/app/services/ai_parser.py:229,234,248`, `bot/app/bot/handlers/safe_flow.py:166`, `bot/app/core/config.py:17`.
**Триггер:** AI_PROVIDER=disabled, AI_UPLOAD_CONSENT=false, существует Groq key; либо распознавание голоса ботом без ключей.
**Наблюдение:** mocks доказали Groq call=1 и Google speech fallback=1. Text-Groq не проверяет ни provider, ни consent; Gemini text не проверяет disabled; «local Google» реально отправляет аудио Google. Voice-handler напрямую вызывает transcribe. Согласие по умолчанию True, что также противоречит явному opt-in.
**Влияние:** речь/финансовый текст/названия счетов уходят поставщику вопреки настройкам. Аудит не отправлял эти данные поставщикам.
**Исправление:** единый gate перед любой отправкой; consent по умолчанию False; отдельное явное согласие на выбранного поставщика, лимиты до download/transcribe.

### A03 — P1: встроенные финансовые записи доступны всем браузерам

**Место:** `frontend/src/api/client.ts:18,222`, `frontend/src/App.tsx:65`, storage keys `client.ts:512,653,862`.
**Триггер:** открыть приложение с новым/неавторизованным профилем либо переключить Telegram-пользователя на том же origin.
**Наблюдение:** в production bundle встроены идентификатор владельца, подробные счета, остатки и история, выглядящие как персональные данные. Кэш не разделён по авторизованному владельцу. Чистый браузер получает эту книгу; при смене пользователя кэш продолжает участвовать в merge.
**Влияние:** раскрытие встроенных данных и смешение профилей. Не установлено, являются ли суммы реальными; наличие подробных записей подтверждено, поэтому в отчёт сами записи не скопированы.
**Исправление:** удалить персональные fixtures из продукта, демо сделать явно синтетическим и отдельным; cache scope по авторизованному ID, очистка сессии/кэша при смене владельца. Историю Git отдельно проверить до публикации.

### A04 — P1: локальный frontend обращается к внешнему серверу и не умеет локальный вход

**Место:** `frontend/src/api/client.ts:3`, `frontend/src/hooks/useTelegram.ts:98`, `frontend/vite.config.ts:9`.
**Триггер:** обычный локальный запуск без VITE_API_URL.
**Наблюдение:** API_BASE — фиксированный Render origin, а не локальный `/api`; Vite proxy отсутствует; браузер отправляет `tma demo:999999`, которого серверный auth не принимает. Локальный token endpoint не вызывается. `host:true` в обычном npm dev слушает все интерфейсы.
**Ожидание:** локальная разработка использует loopback API и отдельный разрешённый локальный вход.
**Исправление:** same-origin `/api` + loopback proxy, явный local login, loopback host. В браузерном аудите после обнаружения API принудительно переключён на недоступный loopback; внешние записи не выполнялись.

### A05 — P1: ошибка создания/удаления маскируется под успех

**Место:** `frontend/src/api/client.ts:1015,1063`, `frontend/src/App.tsx:177,248,466`.
**Триггер:** POST получает 401/422/409 либо сеть отсутствует; удалить операцию офлайн.
**Наблюдение:** runtime probe HTTP422 create возвращает синтетическую операцию; offline delete возвращает true. App закрывает форму, сообщает успех и сохраняет локальные финансовые изменения до ответа. Повторной отправки надёжной очередью нет.
**Влияние:** пользователь уверен, что запись есть на сервере, но бот/другое устройство её не видят; timeout после фактического commit тоже остаётся неоднозначным.
**Исправление:** ошибки должны быть ошибками; стабильный client_id на retry, состояние pending/error, принятие server response, восстановление UI при отказе. Offline режим требует отдельного явно спроектированного протокола, а не fallback success.

### A06 — P1: frontend не передаёт revision при редактировании/удалении

**Место:** `frontend/src/types/index.ts:31`, `frontend/src/api/client.ts:826,1043,1057`, `frontend/src/App.tsx:277`.
**Триггер:** изменить или удалить существующую серверную операцию.
**Наблюдение:** тип Transaction не содержит revision; mapper его выбрасывает; PUT payload без обязательной revision, DELETE без query revision. Серверный контракт `bot/app/schemas/finance.py:113` требует revision. Отказ API скрыт A05.
**Ожидание:** запрос содержит текущую версию, 409 требует обновления данных и осознанного повторения.
**Исправление:** сохранить revision/currency в типах и mapper, передавать в PUT/DELETE, проверять контракт интеграционными тестами.

### A07 — P1: создание и редактирование счёта отправляет запрещённые поля

**Место:** `frontend/src/App.tsx:471,489,514`, `frontend/src/components/modals/EditAccountModal.tsx:75`; `bot/app/schemas/finance.py:41,45`.
**Триггер:** создать счёт или сохранить его изменения.
**Наблюдение:** создание отправляет локальные id/user_id; strict AccountCreate запрещает их. Редактор отправляет balance; AccountUpdate не допускает изменения balance, а также id. App игнорирует отказ и успешный server ID, сохраняет локальный `acc-*`.
**Влияние:** счёт существует только локально; последующие серверные операции с ним отвергаются.
**Исправление:** отдельные create/update DTO, balance только как opening balance при create, использовать возвращённый сервером объект и ID. Изменение остатка — отдельный осознанный финансовый сценарий, если он нужен продукту.

### A08 — P1: категории не синхронизируются и имеют чужие серверу ID

**Место:** `frontend/src/api/client.ts:979`, `frontend/src/App.tsx:564`, `frontend/src/components/transaction/AddTransactionScreen.tsx:281`.
**Триггер:** загрузка/создание/переименование категории и сохранение расхода.

**Влияние:** UI расход/перевод может оказаться серверно невалидным; категории бота и приложения расходятся.
**Исправление:** реальный category CRUD и server IDs, null category для переводов; не смешивать subcategory-строки с серверной parent_id моделью без согласованного контракта.

### A09 — P1: серверные изменения истории проигрывают старому кэшу

**Место:** `frontend/src/api/client.ts:775,786,703`.
**Триггер:** загрузить операцию, изменить её ботом, снова загрузить приложение.

### A10 — P1: постоянные локальные остатки перекрывают сервер, удалённые счета возвращаются

### A16 — P1: подтверждение черновика в новой SQLite-сессии падает

## UX и дизайн

Визуальное впечатление: компактный мобильный бюджет с читаемой главной суммой, карточками категорий и удобной цифровой клавиатурой. На320/375px проверены dashboard, settings и форма; глобального горизонтального overflow не обнаружено на проверенном dashboard. На1280px выполнен просмотр. Это не подтверждение всех sheets или физического Telegram.

Основной дизайн-дефект — ложная обратная связь о статусе денег: успех до серверного сохранения, «записан» у черновика, отсутствие offline/error/auth состояния, автоматические AI записи. Они важнее вкусовых правок цвета/скруглений. Канонический Figma файл не предоставлен, pixel-perfect соответствие не проверено.

Рекомендуемый текстовый сценарий для следующего этапа: загрузка/вход → реальные счета или пустое состояние → форма/AI предложение → проверка суммы, валюты, категории и счетов → сохранить → pending → server confirmed либо видимая ошибка с сохранённым черновиком. Dashboard: остатки отдельно по валюте, выбранный месяц, серверные итоги, история с пагинацией. Текущий визуальный язык сохранить; не начинать с переработки карточек.
