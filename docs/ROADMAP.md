## Какие идеи взяты из похожих продуктов

Actual Budget: отдельный импорт, правила сопоставления, явная сверка, осторожная обработка повторов и связанных переводов.
Firefly III: стабильные идентификаторы импорта и различие банковского ID и вычисленного совпадения.
GnuCash: валютная операция требует разных сумм по двум счетам; RUB иUSD нельзя механически складывать.
Это исследованные идеи, а не копирование чужой реализации. Ссылки и применимость — docs/audit/09_COMPARABLES_AND_BANK_SOURCES.md.

## Единая гипотеза банковского импорта

Банк/выписка → ограниченный адаптер → неизменяемые исходные поля и fingerprint → сохранённый черновик → решения человека «добавить/исключить/комментарий/категория» → атомарное подтверждение → сверка.
Реализован канонический CSV-этап. Прямые банковские API не обещаны: публичная спецификация сама по себе не даёт боту доступ к личным счетам.
XML не универсальный банковский формат; перед реализацией нужны банк, вид счёта, реальный обезличенный образец и правила выгрузки.

## Дисциплина каждого изменения

Одна задача → небольшой план и критерии → тест реального дефекта → изменение → независимое ревью, когда доступно → quality → обновление feature docs.
Файлы делить по ответственности, не по случайному числу строк. Порог500Python/300TS — сигнал и автоматический gate, исключение должно иметь причину и предел.
Не переписывать работающую систему ради модного фреймворка. Текущий стек поддерживает один backend для бота и веба; Postgres добавлять по реальной нагрузке/эксплуатационным требованиям.
