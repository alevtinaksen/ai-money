# Работа над проектом

Новая задача: сформулировать результат пользователя → найти владельца поведения → определить регрессию → изменить один связный участок → проверить → обновить документацию. Сначала обдумать контракты, пограничные случаи и обратимость. Количество потраченных минут не является доказательством качества.

Модули группируются по функциям продукта, а не по произвольным кускам одинаковой длины. Python 500 строк, JS/TS 300 строк — повод пересмотреть ответственность. `scripts/structure_check.py` проверяет bot/app, frontend/src и scripts. Архивы, зависимости, сборка и миграционные выгрузки вне этих каталогов не выдаются за проверенный прикладной код.

Для оправданного исключения добавить путь, max_lines и reason в structure-exceptions.json. Исключение не разрешает бесконечный рост: при превышении записанного размера gate падает. Указать реальную причину и необходимую регрессию перед будущим выделением. Не добавлять исключение только ради зеленого отчета.

Проверка имен требует snake_case для Python (включая допустимые dunder), PascalCase для React JSX/TSX в components (кроме test/spec), отклоняет source-копии с copy/backup/duplicate/final2 в имени. Реальная функция scripts/backup.py и ее тест имеют точечное исключение, поскольку это резервное копирование данных, а не дубликаты исходника. Проверка не доказывает правильность архитектуры по одному имени.

При каждом PreInvocation проектный hook запускает этот же read-only scan и добавляет в контекст до восьми кратких findings. Он пишет только marker активации, не исправляет имена или исходники сам. Изменения делает модель с проверкой импортов и регрессий; недоступное чтение отмечается UNVERIFIED.

Роли команды: планирование контракта, реализация, тестирование, проверка, документация. Навыки задают эти процессы. Они не создают независимые процессы автоматически. Субагенты IDE не подтверждены текущей документацией; настоящий параллельный запуск зависит от доступных инструментов конкретного клиента.

Примеры для проверки инструкций: «разбей большой компонент» должно начать с контрактов и регрессий; «сделай новую функцию» должно включить документацию и тест поведения; «всё готово?» должно дать реальные результаты quality, а не чтение файлов. Эти сценарии записаны как критерии; живой прогон модели на Mac не проводился.
