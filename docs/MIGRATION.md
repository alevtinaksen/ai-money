# Резервные копии и перенос существующих данных

Старая база не должна автоматически превращаться в новую. `bot/app/core/database.py:init_db` отказывает в запуске базы с таблицами без schema_version, а также неизвестной версии. Это намеренная защита финансовых данных. Не добавляйте schema_version вручную и не удаляйте старую базу для обхода ошибки.

## SQLite backup

Из корня проекта выполните, указав новое имя для каждой копии:

```sh
python3 scripts/backup.py backup bot/finance.db backups/finance-before-change.db
```

Скрипт использует SQLite backup API: зафиксированные изменения в WAL входят в согласованную копию. После копирования выполняется integrity_check; рядом сохраняется manifest с SHA-256, размером, временем и результатом проверки. В manifest нет таблиц, финансовых записей, конфигурации или секретов. Сама база содержит личные данные: backups исключен из Git, но это не шифрование; храните копию в защищенном месте. При длительной занятости базы операция завершается ошибкой, повторите в спокойный период.

Для иной DATABASE_URL передайте реальный путь используемой SQLite-базы явно. Скрипт не читает .env и не угадывает источник. Для PostgreSQL этот инструмент не подходит: нужен отдельный проверенный dump/restore для PostgreSQL.

## Проверка восстановления

```sh
python3 scripts/backup.py restore backups/finance-before-change.db backups/finance-restored.db
```

Восстановление проверяет manifest, SHA-256 и integrity_check, затем создает **новый** файл. Существующий файл назначения не перезаписывается, действующая база не переключается. Команда печатает DATABASE_URL для нового файла. До переключения остановите API и Telegram-процесс, проверьте суммы и количество записей. Только затем явно измените DATABASE_URL в bot/.env и перезапустите процессы. Контрольная сумма обнаруживает изменение относительно manifest, но не защищает от злоумышленника, который подменил оба файла.

## Переход со старой схемы

Исходный архив сохраняется отдельно как исторический оригинал; этот скрипт его не изменяет. Архив исходников не равен резервной копии вашей действующей базы.

1. Сохранить старую базу через backup и успешно восстановить отдельную пробную копию.
2. Экспортировать данные старой схемы в изолированной среде: пользователи, счета, начальные остатки, категории, операции и переводы. Не коммитить экспорт.
3. Определить явное соответствие старых и новых идентификаторов, валют, округления, знаков и пар переводов. Не рассчитывать остатки повторно поверх уже сохраненного итога.
4. Импортировать в отдельную новую базу проверенным адаптером. Универсальный адаптер миграции в комплекте **не реализован**.
5. Сверить количество операций, суммы доходов/расходов/переводов и каждый конечный остаток по пользователю/счету/валюте. Расхождения должны быть объяснены до переключения.
6. Остановить записи, повторить финальную сверку и явно переключить DATABASE_URL. Старую базу и backup сохранить для отката. После новых записей откат тоже требует согласования данных.

Синтетические тесты backup/restore есть в scripts/tests/test_backup.py. Проверка на реальных пользовательских данных и macOS не проводилась.


## Новый пустой бюджет рядом со старым PostgreSQL

Если владелец явно решил не переносить тестовые данные, сохранить оригиналы и копию, подготовить новую закрытую схему из текущих ORM-моделей и переключить DATABASE_SCHEMA. Старые public-таблицы остаются неизменными; не добавлять в них schema_version. Версия нового namespace задаётся только вместе с созданием всей актуальной схемы. Приложение не создаёт сам namespace и отказывается от неизвестной/неоднозначной версии. Деньги новой схемы — BIGINT в копейках, включая начальные остатки; старый numeric нельзя копировать как готовые копейки.

Логический JSON-снимок отдельных таблиц — дополнительная копия, не полный PostgreSQL dump. Не заявлять восстановление без проверки. После первого нового сохранения откат требует учёта новых операций, даже если старые таблицы сохранены.

## Реестр повторного создания — выпуск 9 октября 2026

[`scripts/sql/2026-10-09-entity-creations.sql`](../scripts/sql/2026-10-09-entity-creations.sql)
добавляет только entity_creations в поддерживаемую ai_money_v2/version2. Запускать от
владельца схемы после копии и проверки восстановления. Скрипт использует транзакцию,
проверяет единственную version2, владельца и сохранность прежних строк восьми таблиц;
ошибка откатывает DDL. Уже существующая таблица обязана иметь ожидаемые типы/NOT NULL/составной PK; владелец/RLS/права проверяются до COMMIT. Новая таблица включает RLS, права PUBLIC/anon/authenticated
отозваны. Сервер-владелец использует прежние права; новые клиенты прямого доступа
не получают. Откат приложения не требует удаления этого совместимого реестра.

В этом выпуске логический снимок всех восьми таблиц настоящего бюджета сохранён в
ignored backups с SHA-256/правами0600. Его строки восстановлены в **новую локальную
PostgreSQL-схему** и сравниваются канонически, включая целые копейки, даты, foreign keys
и служебные черновики. Это проверенный restore данных приложения, **не полный dump
Supabase**, не копия auth/storage/roles/extensions и не настройка регулярного backup.
Снимок не попадает в Git; хранение локально не является шифрованием.

Синтетические PostgreSQL17.11 пробы покрывают параллельные account/category/transaction
retries, дробные списания, переводы, конкурирующие edit/delete, category cycles,
confirm Telegram/CSV и сверку каждого остатка с журналом. Результаты/ограничения
фиксируются в отчёте выпуска; успешный SQLite quality не подменяет эти пробы.
